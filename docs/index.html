WebFidelity

How much of a web page survives the scrape? AI agents read the web through scrapers, and when a scraper silently drops content, the agent answers from half a page. This project measures that loss, mainly in Firecrawl.

1. Default scrapes snapshot about 300 ms after load

Content that JavaScript adds later is dropped, and nothing in the output says so: the heading and a "Loading..." line come back looking like a finished page. Setting waitFor fixes it every time.

On a real site, quotes.toscrape.com/js-delayed with a 2 s delay scored 0% by default and 100% with waits.

2. In-flight API calls aren't awaited

Our page server logs show Firecrawl's browser does send the page's API request, about 0.25 s after load. It then takes the snapshot before the response arrives. A plain Playwright scraper that waits for the network to go quiet gets everything.

3. The browser window is 100,000 px tall

Asked from inside the page, Firecrawl's browser reports innerHeight = 100000 and scrollY stays 0 after every scroll action. That makes "when it comes into view" lazy-loading fire immediately, which is clever. But feeds that load on scroll events never load, and scroll actions do nothing.

Actions fix most of it, at no extra cost

Re-scraping with waits and a click on any "Show more" button costs 1 credit per page, the same as a plain scrape. On the synthetic bench it fixes everything except finding 3.

On the normal web, Firecrawl does well

On real sites the answer key is a patient local browser: wait for the network to go quiet, scroll until the page stops growing, and load it both before and after the Firecrawl scrape so that content changing by the minute doesn't count as missed.

A detector that didn't generalize

Can you tell that a scrape is incomplete without an answer key? A rule-based detector looked strong on synthetic pages, then fell apart on real held-out sites. Reading a site's external JS files didn't help either: scroll code shows up in 56% of complete sites and 60% of incomplete ones. A third version added one targeted signal and was tested on a fresh set: zero false alarms, but it still missed 5 of 6.

Proposal: the signal that would make this reliable is one only the renderer has: how many requests were still pending, and how long the page had been quiet, when the snapshot was taken. Exposing that in response metadata would let callers retry only the scrapes that need it.

Mistakes caught along the way

  • Rate-limit errors were scored as 0% recall, which produced a fake "unstable" result. Errors are now excluded.
  • The first synthetic infinite-scroll page was broken (Chrome's scroll anchoring). Its results are marked invalid.
  • The first real-site scorer tripped on markdown links, page drift and boilerplate: Hacker News scored 17%, and the corrected figure is 98%.
  • Blind "Show more" clicking broke two real sites, so the click step now targets only buttons with plain selectors.
